# ADR-008: Reviewer isolated by job, checkout, model, prompt and permissions; approvals need evidence

**Date:** 2026-11-24 · **Status:** Accepted · **Decision area:** D8 Reviewer independence

## Context
A reviewer that sees the implementer's reasoning tends to adopt it; a reviewer from the same model
shares its blind spots; a reviewer prompted to "review" tends to approve. The assignment requires
the reviewer to see only the issue, the diff and the repo at the PR head.

## Decision
- **Own job** (`review.yml`), fresh runner, `actions/checkout` of the PR head, `permissions:
  contents: read, pull-requests: write`; posting the review is done by code, not by the agent.
- **Own information:** issue text + `git diff main...HEAD` + the repo. No spec, design, test report,
  PR description or transcript (ADR-003).
- **Own model family:** Nemotron-3 Ultra vs MiniMax for the builders (ADR-006).
- **Own prompt:** the reviewer is told its job is to find reasons the change is wrong or incomplete,
  to run the tests and at least one check of its own, and to cite evidence for every finding.
- **Anti-rubber-stamp rules in code:** an `approve` without any command run is turned into
  `request_changes` ("no evidence"); the verdict must list each requirement from the issue with how it
  was verified.
- **Calibration:** the reviewer is run on five seeded PRs (three with planted defects, two correct)
  to measure catches and false alarms (`experiment/seeded_prs/`).

## Alternatives considered
- **Same job, new conversation.** Cheaper, but the workspace would still hold the artifacts and the
  credentials of the stages job.
- **Reviewer sees the PR description / design.** More context for judging intent; but it is exactly
  the anchoring we want to avoid. Tested in experiment E1.

## Consequences
- The reviewer must rediscover intent from the issue alone; it may flag things the spec deliberately
  decided. That is acceptable: the human sees both.
- A GitHub Actions bot cannot formally approve or request changes on a PR it opened, so the verdict is
  posted as a review comment with a clear `Verdict:` line.
