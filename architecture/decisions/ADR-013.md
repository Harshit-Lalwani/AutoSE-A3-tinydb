# ADR-013: The design check verifies files strictly and records unknown functions as new

**Date:** 2026-11-24 · **Status:** Accepted · **Supersedes:** [ADR-007](ADR-007.md) (stage 2 row only; the
other checks are unchanged) · **Decision area:** D7 Checks

## Context
ADR-007 made the stage-2 check fail when a function named in the plan's JSON block was not defined in
its file, unless the plan listed it under `new_symbols`. The first four runs on GitHub (issues #2, #3,
#4, #5; runs 45420033974, 45420731307, 45420740846) all stopped at stage 2:

| Run (issue) | Attempt 1 | Attempt 2 |
|---|---|---|
| #2 string IDs | `Table._normalize_doc_id` not found | same |
| #4 append | no JSON block (step budget hit, final answer was tool-call text) | `append` not found |
| #5 sorting | `Table._get_field_value`, `Table._sort_docs` not found | no JSON block ("design.md has been updated") |

In every case the plan was reasonable: the "missing" functions were helpers or features the plan
*adds*. The check was right that they did not exist and wrong to treat that as an error; the agent
did not follow the `new_symbols` convention even after the check output told it to. Each failed design
attempt cost about 4 minutes and 270k tokens.
Two other causes showed up: the design agent spent its whole 25-step budget exploring and then wrote
tool-call syntax instead of the plan, and on a retry it answered as if `design.md` were a file it had
edited.

## Decision
- Stage 2 check: every planned file must exist (or be marked `new`), and every file must name at
  least one function or class. Named symbols found in the file are recorded as *changed*; the others
  are moved to `new_symbols` and recorded as *new* in `design.json`. The plan is not rejected for them.
- Every agent with tools is told its step budget in the system prompt; the forced final answer asks
  for plain text.
- The retry feedback says explicitly that the reply *is* `design.md`.

## Alternatives considered
- **Keep the strict rule and improve the prompt.** The prompt and the check feedback already named
  `new_symbols`; two attempts per run ignored it. More prompt text is the weaker fix.
- **LLM judge for the plan.** Could judge whether the plan is sensible, but it is a new unverified
  opinion and costs a call; the code check still catches the error that matters (a non-existent file).
- **Drop the symbol check.** The assignment asks that the plan names files *and* functions; we keep the
  requirement that functions are named, and the changed/new split is useful in `pr.md`.

## Consequences
- The design check is weaker: a misspelled existing function now counts as a "new" function. The build
  and test checks catch a plan that edits the wrong function; the reviewer sees the diff.
- Lesson: a check whose failure the producing agent cannot fix by retrying only wastes the budget. A
  check should reject things that are actually wrong, not things that break a format convention.
