# ADR-002: A fixed state machine in code, chained Actions jobs for review rounds

**Date:** 2026-11-24 · **Status:** Accepted · **Decision area:** D2 Control flow

## Context
The stages are fixed by the assignment, and so are the loops: tests fail → implement again;
reviewer finds an approach problem → design again; at most two review send-backs. What varies is
only *which* backward edge is taken. GitHub Actions jobs cannot loop, but a job can be repeated a
fixed number of times with `needs:` and `if:`, and a reusable workflow avoids copying YAML.

## Decision
- Stages 1–5 run in **one job** driven by `orchestrator.py`, a small explicit state machine
  (`spec → design → implement → test → release`, with `test → implement` and
  `test → design` back-edges). Code, not an LLM, decides every transition, using the stage check
  results (ADR-007) and fixed budgets (ADR-009).
- Review rounds are **separate jobs** chained statically in `autose.yml`:
  `gate → stages → review_1 → fix_1 → review_2 → fix_2 → review_3`. Each `fix_k` re-enters the
  same state machine at the stage the reviewer named (`approach` → design, `code` → implement)
  and runs only if the previous review requested changes. `review_3` is the last word; if it still
  requests changes, the run ends and the human decides.

## Alternatives considered
- **LLM planner/orchestrator** that picks the next stage. Rejected: the graph is known in advance,
  so a planner adds cost and a new failure mode (skipping a check) without adding a decision we need.
  A planner also has to read every artifact, which brings the issue text into the controlling context.
- **Separate workflows that trigger each other** (`workflow_run` / `repository_dispatch`). Gives
  unbounded loops and a cleaner YAML, but one maintainer request is spread over several runs, which
  is harder to follow on GitHub and harder to cap.
- **Everything in one job, including review.** Rejected: the reviewer must have different
  permissions and a fresh checkout (ADR-008), which in Actions means a different job.

## Consequences
- One Actions run shows the whole story; job names say which round each step belongs to.
- The number of review rounds is fixed in YAML; changing it means editing the job chain.
- The reviewer, not the orchestrator, chooses the category of a problem; the orchestrator only maps it
  to a stage. A wrong category costs one round.
