# ADR-001: Four narrow agents for stages 1–4, deterministic release, one independent reviewer

**Date:** 2026-11-24 · **Status:** Accepted · **Decision area:** D1 Splitting the work

## Context
The six stages need different inputs and different powers. Stage 1 needs only the issue and the
public API; stages 3 and 4 need write access to the repo; stage 5 needs a GitHub token but no
judgement; stage 6 must not share anything with stages 1–4. The models we can afford (free NIM
tier, see ADR-006) are mid-sized: in A2 a strong model handled a whole task in one context, but
mid-sized models lose track of instructions as the context grows past a few tens of thousands
of tokens, and a single long conversation would carry the issue text (untrusted, ADR-009) into
every step.

## Decision
- **Spec agent** (stage 1): one chat call, no tools, the A1 SRS skill as system prompt.
- **Design agent** (stage 2): reads `ARCHITECTURE.md` and the code, cannot change files.
- **Coder agent** (stage 3): edits code following `design.md`.
- **Tester agent** (stage 4): writes one test per acceptance criterion from the spec, in a fresh
  context, without the coder's conversation; may not be edited by the coder.
- **Release** (stage 5) is plain Python, not an agent: pushing a branch and opening a PR has one
  right answer and needs the token we keep away from all agents.
- **Reviewer agent** (stage 6) in a separate job (ADR-008).

## Alternatives considered
- **One agent for everything.** Simplest, and the A2 runs show a single agent can solve tinydb
  tasks. Rejected because the agent that writes the code would also write the tests that judge it
  (it can fit tests to its own bug), because one context would accumulate the issue text, all tool
  output and every retry, and because the stage artifacts would be self-reports rather than hand-offs
  we can check.
- **One agent per stage, release included.** Rejected for stage 5 only: an LLM adds risk (it would
  need the token) and no value.
- **Coder writes its own tests (3+4 merged).** Cheaper by one agent. This is the main rival and we
  test it in experiment E2 (`experiment/variants.md`).

## Consequences
- Each agent has a short, single-purpose prompt and a small context; the spec and design are
  checkable artifacts, not thoughts inside one conversation.
- More model calls and more hand-off text to design (ADR-003); the tester and coder can disagree,
  and we need a rule for who wins (ADR-007: the spec wins, the coder cannot edit the tests).
- Five LLM roles but only two model families (ADR-006).
