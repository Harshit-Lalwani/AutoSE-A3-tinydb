# ADR-005: Agents get a bash tool (plus write_file) in a credential-free sandbox user; GitHub is code-only

**Date:** 2026-11-24 · **Status:** Accepted · **Decision area:** D5 Tools

## Context
The agents need to read code, edit it and run tests. GitHub actions (push, PR, comment) need a
token. Tools can be offered as an MCP server (e.g. GitHub MCP), the `gh` CLI or the REST API.
A tool an agent holds is a tool an injected prompt can use.

## Decision
- Agents run in our own ~150-line loop (`workflow/agent/agent.py`, OpenAI-compatible tool calling)
  with at most two tools: `bash(cmd)` and `write_file(path, content)`. The spec agent has none.
- Every agent command runs as an unprivileged Unix user `agent` (`sudo -u agent env -i …`) in the
  workspace, with no GitHub token, no API key, a 120 s timeout per command and output truncated.
- Read-only roles (design, reviewer) are enforced by checking `git status` afterwards and discarding
  changes; the reviewer job also has `contents: read` and no stored credentials, so it cannot push even
  if it tried.
- All GitHub operations are done by deterministic code with the `gh` CLI, in steps that receive
  `GITHUB_TOKEN` through `env:`; `actions/checkout` uses `persist-credentials: false`.

## Alternatives considered
- **GitHub MCP server for agents.** Convenient, but gives agents GitHub write tools we would then
  need to restrict per tool; our agents never need to talk to GitHub.
- **Ready-made agent harness (mini-swe-agent, Claude Agent SDK).** Fine options; we chose our own
  loop to control exactly which tools and environment each role gets and to log tokens per stage.
- **Fine-grained file tools only (no bash).** Safer, but agents could not run the tests.

## Consequences
- Least privilege is enforced by the OS and by Actions permissions, not by asking the model nicely.
- `bash` is still powerful inside the sandbox (network access is not blocked; see limitations).
