**Summary.** Add an `append` operation to `tinydb.operations` that appends a value to a list field, creates the field as a single-element list if missing, and raises TypeError if the field exists but is not a list.

### Acceptance criteria (stage 1, `spec.md`)
- **AC-1** Given the tinydb.operations module, when importing append via 'from tinydb.operations import append', then append is a callable class available in the module's namespace
- **AC-2** Given a database with documents [{'tags': ['a']}, {'tags': ['b']}] and a query matching both, when calling db.update(append('tags', 'c'), query), then both documents have 'tags' equal to ['a', 'c'] and ['b', 'c'] respectively
- **AC-3** Given a database with a document {'name': 'doc'} lacking a 'tags' field, and a query matching it, when calling db.update(append('tags', 'new'), query), then the document becomes {'name': 'doc', 'tags': ['new']}
- **AC-4** Given a database with a document {'tags': 'not-a-list'} and a query matching it, when calling db.update(append('tags', 'x'), query), then TypeError is raised and the document remains unchanged
- **AC-5** Given a database with documents [{'tags': ['ok']}, {'tags': 'bad'}] and a query matching both, when calling db.update(append('tags', 'x'), query), then TypeError is raised on the second document; the first document may or may not be updated (per A-2), but the exception propagates
- **AC-6** Given a database with 3 documents matching a query, when calling db.update(append('field', 'val'), query), then the operation is applied to all 3 matching documents (subject to A-2 error behaviour)
- **AC-7** Given the existing 'add' operation in tinydb.operations, when inspecting the append class signature and usage pattern, then append follows the same protocol: it is a class with __init__(field, value) and __call__(document) that mutates the document dict
